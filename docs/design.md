# Product design

Discodex 1.0 connects Discord to a persistent conversation using a bundled Codex fork. Discord routing, presentation and media belong to Discodex; native execution, memory and child-agent lifecycle remain with Codex. Optional Antigravity execution uses a separately managed AGY CLI with its native subscription login.

## Runtime, data and implementation scope

The fork is tracked as the `third_party/codex` submodule with small patch commits over an official version. It extends provider/executor selection and request compatibility while retaining official tool and child-agent control paths. There is no parallel task manager, duplicate settings database or silent fallback to another model. Discodex adds no file-type/path restrictions or second model-security policy; it handles Discord access, protocol limits, resource ownership and state consistency.

Release CI uses the official Codex package builder to produce the core, code-mode host, `rg` and required OS helpers. The worker and package manifest fix the compatible worker version, fork commit, platform and checksums. The managed executable lives separately from `CODEX_HOME`. The installer offers an existing home (recommended when found) or a separate profile home. Existing profiles keep their selected home, login, memory, session history and settings. Shared `config.toml` is not overwritten. Separate sessions may share a home; concurrent control of the same session is outside this contract.

This document describes the implementation. Published builds and version-specific changes are listed in the [releases](https://github.com/CHOAM-CO/Discodex/releases).

Each profile project also receives `.agents/skills/discodex/`: a short `SKILL.md` in the profile language points to installation and design references bundled from the same build, which the agent reads as needed. Installation, runtime activation during updates and new native app-server connections refresh managed files while preserving existing user-owned skills and user edits; the base prompt and shared `CODEX_HOME` are unchanged.

## Conversation and settings

`/discodex compact` sends `thread/compact/start` for the current persistent thread. Native Codex interrupts any active response and starts manual compaction in the same conversation. Discodex neither creates a new thread nor injects a user message. The command acknowledges that the request was accepted, not that compaction has finished, and displays the native error if submission fails.

The main settings panel exposes **Approval policy** separately from **Permission profile**. The profile default is `on-request`; `never` remains an explicit user choice. Saved and effective policies are shown separately, active threads use the native settings-update API, and thread start/resume receives the selected policy. **Advanced settings** groups the detailed native switches and AGY preferences without duplicating the default-subagent picker. Approval choices are saved per profile in `native-features.json`; they do not overwrite shared Codex configuration.

After a question response is accepted by the native request, the original Discord message shows the selected answer and removes its answer controls. Invalid form input can be corrected before submission. A transport error does not establish whether an answer was received; the actual cause is shown without automatically resending an uncertain response. Late or duplicate clicks cannot submit a second answer or resolve a different question.

The configured home text channel is the persistent conversation surface for ordinary replies, questions, approvals, status, and plans. A worker restart resumes the saved thread. `/discodex new` starts another thread only when requested. Restarting does not promise to preserve an in-progress response or voice call.

`/discodex settings` provides buttons for supported models, reasoning effort, service tier, permission profile, input delivery, voice profile, message receive policy, allow/block lists, and update notifications. Options come from the current native catalog and are checked again when selected. Lists are paginated to fit Discord's limits without dropping options. Detail screens have a Back button to return to the settings menu; Exit closes the settings view. Neither action rolls back settings already applied. Voice choices take effect on the next call. The settings panel and prompts follow the selected installation language.

The message-policy controls can select a receive policy and manage allowed or blocked users and channels. User choices show names or nicknames resolved from the current server, while adding or removing a person uses their account ID. Voice choices come from `thread/realtime/listVoices`. Choosing the Codex default omits an explicit voice so native settings apply. A selected voice is stored in worker state and reused on the next connection.

Slash commands include `/discodex update`, `/discodex settings`, `/discodex voice`, `/discodex status`, `/discodex interrupt`, `/discodex compact`, `/discodex new`, `/discodex voice-join`, and `/discodex voice-leave`. Slash commands and administrative actions retain their configured operator checks. During an active ordinary Discord-message turn, the home channel typing indicator is refreshed and stopped on completion, error, or disconnect.

When native Codex asks a question or requests approval, Discodex displays a Discord form or buttons and returns the response with the original request ID and choice scope. Old controls cannot answer a resolved request or a request from a different connection generation.

## Models and subagent defaults

The main and default-subagent pickers combine the active Codex catalog with explicit provider/model pairs in native config profiles. A `[profiles.NAME]` entry includes both `model` and `model_provider`; a provider definition alone does not enumerate its models. Provider authentication and capabilities stay native. See the [installation examples](installation.md#custom-and-local-codex-providers).

A model selection stores the executor, provider and model together. The fork accepts a child target separately from the parent target, so a child can use another configured provider. It resolves that provider's own configuration and authentication. An unavailable selection remains visible as an error; it is not replaced with the parent model. The main thread keeps its durable history. **Default subagent model** appears once on the settings home. Saved child defaults are loaded on the next thread creation or resume, including after a worker restart. The current thread keeps its effective defaults until resumed, and existing children keep their own configuration.

## Provider changes and encrypted history

Compatible `/models` catalogs can supply each model's context capacity through `context_window`, `context_length`, `max_model_len`, or `meta.n_ctx`. Native discovery, authentication, and provider-specific caches remain in use.

Providers can opt into input token counting with `model_providers.<id>.input_tokens_endpoint`, using the [OpenAI Responses input-token contract](https://developers.openai.com/api/docs/guides/token-counting). The endpoint is configurable as a provider-relative path or absolute URL. Before each ordinary sampling request with automatic compaction enabled, the core counts the prepared full input, instructions and tools after provider compatibility conversion and before WebSocket delta transmission. The provider applies the same template and tokenizer as generation; Discodex does not implement a model-specific tokenizer.

The count is used for the current context-budget decision without replacing recorded usage. When compaction is needed, the existing native flow runs and the prepared request is counted again; a model transition uses the recorded previous model and provider. If the request still exceeds the budget, the core reports an error before generation instead of repeating compaction. A configured endpoint's authentication, transport or response-format failure is reported rather than treated as zero tokens or replaced with an estimate. Without this setting, native usage-based estimation remains unchanged; support is not enabled automatically. See the [provider settings example](installation.md#custom-and-local-codex-providers).

Before sampling with a smaller Codex model, the core compares the context budget and, when needed, compacts with the previous model and provider. The source runtime is retained through resume and context forks. Cross-provider compaction produces a readable summary; it does not assume that providers can replay each other's encrypted checkpoints. Failed compaction preserves the conversation and prevents another request to the destination model. This applies to Codex provider transitions; Antigravity executor compaction is not implemented.

Native context estimation combines reported usage with local estimates. If the first request after a model change returns a structured `context_length_exceeded` error before any response or tool execution starts, the core compacts once with the source runtime and retries within the same turn. It preserves the current user input, including media, without inserting another message. A compaction already performed before sampling is not repeated. Partial responses and executed tools are not replayed.

The same compatibility boundary applies when switching the main provider and when a child forks conversation context into a different provider. Persisted source history and parent snapshots remain unchanged. At request construction, the fork checks `model_providers.<id>.capabilities.encrypted_content` and creates only the supported outbound view. This optional override defaults to the native OpenAI or Azure Responses classification; other providers default to unsupported.

Conversion operates on typed native response items: encrypted reasoning/message payloads, compaction, tool-result content and agent-message content. Readable summaries, text and image siblings, call IDs and ordinary tool results remain associated. Opaque-only parts become an explicit notice that prior content is unavailable and may need to be retrieved or regenerated. The system does not decrypt them or claim the whole context was read. A literal string or ordinary tool JSON key named `encrypted_content` is not recursively removed. These native encrypted payloads are provider-specific replay data, not a generic password-redaction mechanism.

Native `AgentMessage` wire support is separate from `encrypted_content` and is controlled by `model_providers.<id>.capabilities.agent_messages`. When omitted, it follows the core's existing native OpenAI provider classification; custom providers can explicitly override it to match their support for the extension. Without native message support, the outbound view preserves `id`, `author`, `recipient` and readable content in a JSON envelope inside an ordinary assistant message, with an explicit unavailable notice for opaque native content. Original history remains unchanged; this conversion neither rejects the provider/model nor substitutes another one. Even when `encrypted_content` is true, unsupported native agent-message ciphertext receives that notice because its replay format is unavailable.

## Optional Antigravity execution

Antigravity is disabled by default. The installer and **Advanced settings → Antigravity** use the same setup backend to download the official prebuilt CLI into the profile's managed runtime directory and verify its release checksum. Each profile owns its binary; installed external AGY binaries are not reused or overwritten. Setup offers existing settings or a separate profile-local directory through native `--gemini_dir` and `--app_data_dir` flags, placed before the subcommand. These flags separate files, not AGY's native OS account keyring. Uninstall removes the managed binary without logging out or deleting shared AGY credentials and settings.

Setup first checks the catalog and account. When sign-in is required, it starts the normal interactive CLI in an owned PTY and relays its actual prompts, browser link and authorization-code input to Discord or the installer. `agy models` verifies readiness; it is not a first-login command. Browser consent remains a user action. Cancel and Exit stop setup, including its owned login process, without enabling an unverified backend. They do not roll back consent already completed in the browser. Once verified, model targets appear in both pickers. The existing subscription login belongs to AGY; no SDK or private authentication endpoint is used. Preferences apply on the next selection or AGY execution.

When enabled, Discodex reads exact model IDs and labels from the installed CLI’s `agy models` output and effort alternatives from `agy --help`, without sending a model prompt. Both model pickers use those discovered rows; manually configured IDs supplement them. CLI help describes argument choices, not verified per-model capability metadata. Discodex does not derive IDs or remap effort from model names. Catalog failures appear in settings. An explicit unsupported effort is forwarded unchanged and may fail in the CLI; no fallback effort is substituted.

Codex remains the canonical conversation and task store. Each AGY response starts a fresh CLI execution with the native conversation and visible tool-result context replayed into its input. This preserves the recorded context, not AGY's private reasoning or hidden runtime state. Native memory remains in the selected Codex home. Voice transport remains Codex Realtime while AGY can serve as the backing work executor on the same thread.

AGY uses its own tools where they overlap. Missing Discord/task tools are supplied through the project MCP configuration without replacing unrelated entries. MCP task operations enter the Codex fork's official child lifecycle, including status, waiting, messaging and interruption. The integration does not add a second scheduler or guarantee AGY's internal team mode can be disabled. Tests verify data and lifecycle behavior, not a forced model decision to select a particular tool.

Each external response is bound to its native thread, turn and response ID. MCP calls, streamed events and completion responses retain that binding through native dispatch. A late call from an earlier response cannot be attached to the next response, even when both share the same native turn.

## MCP tool-call approvals

An official Codex form elicitation marked `_meta.codex_approval_kind: "mcp_tool_call"` with an empty object schema is shown as execution approval buttons rather than a free-form input form. Discodex offers the approval actions supported by the native request and exposes session-wide or always-allow choices only when the request's `_meta.persist` provides that scope. It passes the selected `action` and native `_meta.persist` through without inventing input or credentials. Ordinary forms remain ordinary input; URL or user-authentication requests are not treated as tool-call approvals. Request IDs, connection generations, and duplicate-response protection remain attached to each pending request. The contract follows Discodex’s pinned Codex fork baseline (`83086188`): [approval form generation](https://github.com/CHOAM-CO/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/mcp_tool_call.rs#L1962-L2023), [approval response handling](https://github.com/CHOAM-CO/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/mcp_tool_call.rs#L2113-L2149), and [app-server response metadata forwarding](https://github.com/CHOAM-CO/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/bespoke_event_handling.rs#L1728-L1753).

## Discord message routing

The configured receive policy determines which senders are authorized: `Everyone`, `RegisteredServer`, `RegisteredChannels`, or `Paired`. Separate allow and block lists remain in effect across policy changes; the block list takes precedence over the allow list. The bot ignores its own messages. Authorization alone does not determine the input path: routing still applies the home-channel, bot-mention, registered-channel/thread, and admitted-DM rules. A mention does not grant sender authorization.

Paired users and users on the allow list can send DMs without mentioning the bot, regardless of the selected server/channel receive policy. The block list and self-message exclusion still take precedence. `Everyone` also accepts other DM senders. Ordinary automatic output, questions, approvals and progress remain in the home channel; to answer a live DM in the same conversation, the agent uses `discord_send_message` with its `source.dm_id`.

DM input includes `source.channel: "DM"`, `source.dm_id`, the author and `source.authorMention`. The same `discord_send_message`, `discord_get_messages`, `discord_search_messages` and `discord_download_attachment` tools accept `dm_id` instead of `channel`, `channel_choice` or `thread_id`. They verify the existing Discord DM channel, preserve the usual pagination, search and file behavior, and accept `channels/@me/...` message links without a guild-member lookup. This selects an existing DM; it does not create a conversation with an arbitrary user.

Accepted messages use the existing input route. Home-channel messages can be linked as Discord replies. Automatic replies, questions, approvals, and progress stay in the home channel. For a conversational reply to a live accepted message received from another channel, use discord_send_message to reply in that source channel; the live message supplies the reply target and intent, so no separate request to send there is needed. Deliver that conversational reply only in the source channel; do not duplicate it in the home channel. Do not attach a message from another channel as a Discord reply to a home-channel message. Historical messages, search results, and forwarded or quoted content do not authorize sending. Other separate messages to another text channel require an explicit user request and use the Discord send tool.

Completed ordinary assistant output and replies sent through `discord_send_message` render Markdown tables as wrapped, paginated PNG attachments, preserving inline bold, italic, underline, and surrounding prose. PNG bytes are generated in memory, use installed system fonts without installer font changes, and are dropped after delivery or failure; rendering failures send the original Markdown unchanged. Each PNG stores the table source in PNG text metadata. The localized **View source** button fetches the PNG from Discord and returns that metadata as paginated, copyable ephemeral text visible only to the clicker. No `.md` attachment or local file/cache is kept; the source survives worker restarts with the PNG stored by Discord.

The native input includes source author, body, and a stable `source.authorMention` token, including for home-channel messages and bot-authored messages. Explicit user mentions are enabled on normal conversational replies so the agent can address the input author. Status, error, and other non-conversational notices suppress mentions. Bot-authored messages include `source.authorIsBot: true` so Codex can distinguish them from human input.

During a voice call, messages in that call's transcript thread can be routed directly into the voice conversation. Other accepted messages that arrive during voice setup, an active call, or teardown are saved in a durable inbox. The call receives a short notification preview; the preview does not mark the item read or request that it be spoken. Inbox messages and attachment details are persisted before download; failed attachments are retried and any continuing failure is reported. An item is marked read only after every attachment is received and the associated native turn completes. The inbox can be read during the call through `discord_read_voice_inbox` when the content is relevant or the user asks. After confirmed teardown, only items still unread are submitted in order once existing native work is idle.

Discord tools can list channels and users, read and search messages, download selected attachments, and send messages. Channel and user names are resolved against current server data; ambiguous results return choices. Message and attachment operations can target a thread by ID, including archived threads, after checking current server access. Message pagination follows Discord cursors and API page sizes; it does not invent a fixed history index. Tool output preserves source IDs and native turn association.

Explicitly selected readable local files can be attached regardless of type or path. Direct message attachments are downloaded before input is submitted. PNG, JPEG, and WebP files are passed as native image input; other files are provided by local path for Codex to read. The app-server does not expose a general binary file turn item, so this is not described as equivalent to a ChatGPT file-upload API. Files linked in completed assistant answers can be delivered as Discord attachments. Discord's actual request limits are handled by splitting delivery; Discodex does not add its own file-type, path, or aggregate-size deny list.

## Voice

`/discodex voice-join` and the agent `voice_join` tool report success only after the actual Codex Realtime WebRTC connection is ready in an allowed voice channel. They carry the context of the same persistent thread. Configured operator audio is sent to Realtime, response audio is played in Discord, and confirmed transcripts are written to a per-call transcript thread. Each call uses its own Realtime session ID while retaining the backing thread ID, so the transcript belongs to that call and conversation context continues.

Discodex sets the managed core's `experimental_realtime_model_provider` to `openai`. This selects the provider and authentication only for the Realtime call and its sideband connection, leaving the thread's main model, provider and executor unchanged. The same thread can therefore use OpenAI, a local/custom provider or AGY for work behind the Codex voice conversation. Voice starts with the native bounded startup context; delegated work uses the persistent thread's model history and returns through the existing automatic handoff. `flushTranscriptTailOnSessionEnd: true` records speech remaining after the last handoff in model history before closing, without starting another model response. Displayed transcript items and model input history remain distinct, and neither a new thread nor a synthetic resume prompt is needed.

The `name` profile setting supplies the text conversation identity on new threads and when resuming a thread after service restart. Realtime voice uses a separate backend identity prompt: the worker passes `experimental_realtime_ws_backend_prompt` to its owned Codex child process. In the pinned core baseline (`83086188`), the [prompt selector](https://github.com/CHOAM-CO/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/realtime_prompt.rs#L5-L24) prefers a non-empty configured override, then the request prompt, then the [default backend prompt](https://github.com/CHOAM-CO/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/prompts/templates/realtime/backend_prompt.md#L1-L3), which identifies itself as Codex. [`realtimeStartInstructions`](https://github.com/CHOAM-CO/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/src/protocol/v2/realtime.rs#L244-L246) instead supplies developer context to the backing Codex model. The backend override does not change global Codex settings. No automatic greeting is injected; voice receives the call boundary and thread continuity, then waits for the user's first utterance.

`/discodex voice-leave` ends the call and reports the actual outcome. When Codex requests hangup, the `voice_leave` tool uses its generated call summary to update the call's captured parent anchor after successful transcript cleanup. Manual `/discodex voice-leave` does not generate or attach a summary. Leaving voice preserves the backing Codex thread and its text conversation.

Normal 20 ms Opus audio is forwarded compressed when possible. Songbird handles Discord-specific RTP headers and encryption. Realtime calls use a unique `realtimeSessionId` for each call while retaining the existing `threadId`, so each transcript belongs to the correct call and conversation context continues. No automatic greeting is injected when the call connects. Unconfirmed transcript text is not published as a confirmed utterance.

Messages with attachments in the active transcript thread enter the same persistent Codex conversation with text and files together. If any required attachment download fails, the message is not partially submitted. Other home-channel messages and bot mentions received during a call remain in the inbox until teardown.

## Work tools and plans

The `discodex_tasks` MCP exposes the official Codex CLI thread tools (`list_threads`, `list_archived_threads`, `read_thread`, `wait_threads`, `send_message_to_thread`, `create_thread`, `fork_thread`, `set_thread_title`, and `set_thread_archived`) and managed-worktree tools (`create_worktree`, `get_worktree_creation_status`, and `list_worktrees`). The tools use the worker-owned app-server process and do not edit the user's global Codex configuration. Other threads remain separate tasks; their replies are not mixed into the profile's home channel or voice transcript.

Native `update_plan` progress is associated with the current thread, connection generation, and turn. Each changed plan creates a distinct Discord Embed card in the home channel; later plans always create new cards and never edit earlier cards. Cards show completed/total counts, completion marks and strike-through for completed items, an arrow for the active step, pending markers, and a status color. Identical event replays are suppressed. Plan titles and step text are preserved in full; when content exceeds Discord limits, it is split across pages at the actual limits without truncation. This progress view is separate from switching Codex into Plan mode.

## Memory

When `memoryEnabled` is `true` in the worker profile, the worker enables the official native memory features, generation and use, and dedicated memory tools. It also aligns the resumed thread's memory mode. If the field is omitted, existing native memory settings apply. This setting affects the worker's Codex child process and does not change global Codex settings or other Codex processes. Native policy determines when memories are created and integrated; each utterance is not guaranteed to be remembered immediately.

## Release updates

Checks use persisted timing: the first check is due immediately, then every six hours after success or 15 minutes after failure. A 15-second loop and wake events schedule checks without creating a model turn. Automatic notices appear only after five minutes of inactivity and offer **Update**, **Skip this version**, and **Never notify again**. This controls notice timing, not confirmed installation.

`/discodex update` checks immediately and shows **Update / Cancel** with an explicit warning that active work, including children, and voice will stop. A confirmed update does not enter an idle queue. The worker asset is downloaded and verified before active work is interrupted; then the incoming updater stages its matching runtime before stopping or replacing the installed service. Runtime preparation can therefore fail after a response has been interrupted. Such failure leaves the installed worker, runtime and profile references intact; it does not silently restart that response.

The incoming helper keeps the 0.1.x executable asset naming and `update-helper` contract. A release adds the official-layout runtime archive and its manifest, pinned to the incoming worker. Staged content is checked before switching owned worker/config/ownership files. On replacement or restart failure, the updater attempts to restore the previous worker, profile configuration, runtime references, ownership record, and service state. If a required recovery step fails, dependent steps stop and the cause is reported; a mixed installation is not restarted. Unused staged runtimes are cleaned up after any required service recovery, and cleanup failures are also reported. Package cleanup removes only recorded, unmodified owned files. Codex home, accounts, memory, history and settings are not copied or erased.

After restart, the home channel reports success or failure independently of notice preferences. No automatic resume prompt or empty-input continuation is inserted. Other devices update only when requested. CI defines Windows/macOS/Linux x64 and ARM64 artifacts, worker checksums, runtime manifests and the source-free installer archive; it does not build on end-user machines. Current published downloads are at the [release page](https://github.com/CHOAM-CO/Discodex/releases/latest).

## Installation ownership

The installer registers a user-scoped Linux systemd user service, macOS LaunchAgent, or Windows logon scheduled task. It records owned resources and only updates or removes those resources. It preserves Codex credentials, threads, projects, Discord history, and external Codex installations. See the [installation guide](installation.md) for setup, migration, update, removal, and platform permissions.

## Advanced settings, plugins, and asynchronous requests

Each Discodex profile owns its `native-features.json`. It enables official app-server capabilities including CodeMode, host, multiagent v2 and `wait_agent`, normal-mode questions, clock, token budget and history notes, and asynchronous notifications. The native feature settings view distinguishes effective native state from saved values and identifies changes that require a restart.

`/discodex plugins` uses the current official native plugin catalog and Discord buttons for its supported read, install, and uninstall operations. Recommendations use official elicitation, and any plugin authentication or approval stays in the native flow. Availability and entitlements are determined by the native app-server and account; the catalog does not imply that every plugin is available to every account.

Native questions can be answered in Discord with buttons or free-form text. Discodex preserves the original question ID and native thread association. Asynchronous notifications are delivered to the home channel without ending the current turn.

The main-control event queue uses a supervised consumer. Profile-scoped logs are persisted, including for GUI-launched Windows workers that have no attached console. Client updates continue to use prebuilt release assets rather than source builds.
